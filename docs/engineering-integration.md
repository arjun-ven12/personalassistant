# Phase 27.3 engineering integration

Phase 27.3 uses the existing Phase 27.1 signed Mac Agent transport and worktree runtime. Integration produces a reviewable candidate in a dedicated `alexa/` worktree; a separate governed owner action can fast-forward that candidate into the registered local protected target branch. It does not push, deploy, publish, or run production migrations.

## Flow and boundaries

The company-scoped `/api/engineering-integrations` routes require authentication; writes additionally require the trusted origin, CSRF token, and verified private transport. Creation accepts a completed Phase 27.2 objective and an idempotency key. The service checks every task result, repository authorization, task/agent/workspace binding, source status, files changed, individual validation and review, and one common base. A deterministic dependency-aware order and file-overlap map are persisted before execution. The source checkout is not modified.

The integration worker takes a fenced PostgreSQL lease. It validates the clean base in the dedicated integration worktree, asks the signed Mac Agent to create one controlled machine-authored commit per source task, and cherry-picks commits in planned order. Each signed cherry-pick names a registered source workspace; the Mac Agent verifies that the supplied commit equals that source worktree's HEAD. Repeated commit preparation and already-applied cherry-picks are recognized for crash recovery. Conflicts are classified deterministically and bounded hunk locations are retained. Only non-sensitive, unprotected Markdown conflicts with one conflicting file are eligible for an AIRouter coding-role/medium-complexity (Terra-policy) classification. A confidence of at least 0.9 permits a separate finite Mac operation to prove both versions are append-only against the same commit parent and combine their tails. The model never writes file content or Git commands. Native proof failure, missing bounded context, other conflict classes, or two failed advisory attempts escalates; the cherry-pick is aborted and the integration worktree remains isolated. No unbounded Git or shell capability is exposed.

The full registered repository validation profile runs against the combined head. When both bounded validation reports are available, stable command/test identities classify failures as `PRE_EXISTING`, `NEW_REGRESSION`, `RESOLVED`, or `UNKNOWN`; unstructured prose, unavailable commands, and saturated failure lists stay `UNKNOWN` and never waive the full PASS requirement. An owner-registered source-to-generated-path binding provides one lightweight deterministic contract check: changed schema sources without their bound generated output block the run. No inferred schema relationship is treated as proof. A bounded base-to-head diff is obtained through the same signed transport, screened by the existing lightweight secret redaction, compared with expected changed files, and supplied to an independent AIRouter review. Sensitive paths and high-risk tasks require a separate security reviewer. Workforce matching ranks eligible reviewer definitions; repository authorization, assignment, company scope, and separation from authors/manager remain hard gates. Reviewers cannot execute operations. Acceptance evidence must be cited per criterion; a generic passing test is not automatically treated as acceptance proof. Actual head, branch, and cleanliness are checked after validation and review. The final READY run and merge candidate are committed atomically under the lease fence.

On combined validation failure or ordinary independent-review `CHANGES_REQUIRED`, the integration run retains its evidence and enters `REPAIRING`. The existing Engineering Manager creates one deterministic repair task for the smallest identifiable parent task. Its normal Workforce matching, Agent OS session, isolated worktree, AIRouter worker, task validation, and review remain in force. After it completes, the same integration run adds only that result and reruns combined validation and required reviews. The limit is one to three repair cycles; exhaustion enters `BLOCKED` for owner escalation. Security-review `BLOCK` remains fail-closed.

The candidate exposes the branch/head/base, included tasks, changed files, bounded diff summary, validation and review IDs, findings, token/cost details in review records, and acceptance evidence. READY is not authorization to merge. `POST /api/engineering-integrations/:runId/merge` requires the existing short-lived, session-bound recent-authentication approval for a canonical candidate/base/head/target/idempotency digest. The signed execution verifier rechecks company, repository, integration workspace, candidate status, lease generation, approved action, passing validation and distinct required reviews. The Mac Agent accepts only a clean checked-out registered target with the exact expected base and candidate worktree head, then performs a local fast-forward only. A moved target marks the candidate STALE. Same-key retries recognize the already-merged head; an uncertain signed result retains the merge lease until expiry, and the signed native request expires with that lease. No force push or protected-branch bypass is available.

## Fail-closed limitations

- Automatic resolution is intentionally limited to independently appended Markdown. Import ordering, fixtures, structural conflicts, security-sensitive areas, contract semantics, and unknown conflicts still escalate. Repair workspaces start from the registered repository base and are cherry-picked into the integration head; a fix that requires editing combined-only code may need owner-directed reintegration rather than an automatic repair.
- The change map identifies same-file overlap and actual Git change kinds, but does not reliably distinguish same-region from different-region edits or independently prove API/schema semantic compatibility. The explicit generated-client binding check is intentionally narrow; combined validation and independent review remain authoritative.
- Baseline comparison does not normalize arbitrary compiler output or claim that a matching failure excuses an integrated validation failure. A failed combined validation cannot produce READY.
- Candidate review is limited to a 128 KiB bounded combined diff; truncated, binary, or secret-redacted changes fail closed for owner handling. This uses the existing lightweight scanner, not a comprehensive secret-detection system.
- Creation idempotency is persisted, but a simultaneous first-create race before the integration run record is written can contend on worktree creation. There is no atomic creation reservation yet.
- Integration and merge lease fencing prevent stale database publication. The merge transport also carries a signed lease generation and expiry, which the verifier and Mac recheck before mutation. Other long-running native operations still do not have a Mac-side lease token.
- Implementation/repair costs remain in Phase 27.2 task and objective records; conflict-resolution and review costs are in the integration run and review records. A single objective-wide roll-up is not implemented because naively adding repair costs would double count task results. This is non-blocking economics presentation work, not a second billing system.
- A live trusted online Mac Agent execution is not demonstrated by these tests. Native Git operations use temporary repositories, signed transport is covered separately, and service tests use a bounded fake gateway/reviewer.

These limitations and missing live trusted-Mac acceptance prevent the `PHASE 27.3 VERIFIED COMPLETE` verdict. A READY candidate alone never mutates the target branch.
