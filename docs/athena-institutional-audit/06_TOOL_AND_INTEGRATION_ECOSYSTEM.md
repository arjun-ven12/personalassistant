# Tools, adapters and external integrations

> Audit date: 2026-10-26 · CONFIDENTIAL INTERNAL · Review draft v0.1
> Evidence scope: current workspace, including pre-existing uncommitted changes.
> Current implementation, test evidence, and proposed institutional design are distinguished below.

## Three concepts that must stay distinct

A **tool declaration** describes a finite schema, risk and approval requirement. A **provider implementation** performs one reviewed operation. A **configured binding** connects an authorized company/account to that provider through a secret reference and permission grant. None of the three alone proves the other two exist or that an external operation succeeds.

The source-controlled tool catalog is `governance/defaults.ts::BUILT_IN_TOOLS`; `GovernanceService` and `PolicyEngine` evaluate trusted state. `IntegrationRegistryService` handles integration metadata and explicit capability permissions. `BusinessOperationsRuntime` handles finite business requests, binding resolution, policy/approval/stop checks, execution claims, provider calls, verification and reconciliation. It is not a universal arbitrary API proxy.

## Native and application adapter stack

`ApplicationRegistryService` manages trust, capabilities and permissions; `AdapterRegistryService` records SDK lifecycle/sandbox/compatibility; `CoreAdapterService` maps semantic actions; `NativeProviderRuntime` validates and dispatches reviewed provider capabilities. `apps/mac-agent/electron/native-providers.ts` declares separate **implementedCapabilities** and **unsupportedCapabilities**. Backend capability catalogs are wider than actual native coverage.

Examples from source: VS Code launch/focus and selected semantic editing exist, while opening repositories/files, saving and many panel/tab commands remain explicitly unsupported in that provider descriptor. Finder implements launch/focus and fixed Desktop/Downloads routes while several file/folder operations remain unsupported. Browser semantic actions depend on the finite native bridge and exact target verification. A `provider.terminal` backend descriptor is not evidence of an implemented terminal Provider Host entry. The independent engineering command runtime is not a generic Terminal adapter.

Native host launch uses fixed reviewed Launch Services commands and provider-owned bundle/process identifiers. Semantic interactions go through `NativeSemanticInteractionBridge`; raw handles, coordinates and unrestricted Accessibility are prohibited. Success checks differ: process-family liveness is weaker than verifying focused UI state or semantic mutation. Documentation must state the actual verifier used for each operation.

## Business dispatch lifecycle

`BusinessOperationsRuntime.request` validates the discriminated action schema, resolves provider and exact integration capability, company credential binding and permission, computes digest/idempotency, creates approval when required, atomically claims dispatch, rechecks current boundaries before provider invocation, records result/mapping/metric lineage and emits bounded audit. Commercial operations add resource leases, version expectations and per-currency aggregate controls. `reconcile` handles persisted external receipts; webhook ingestion validates signature/timestamp and stores canonical event relationships.

Current hardening code contains `assertWriteExecutionAllowed`, `assertCurrentApproval`, and `authorizeDispatch`; older audit findings that those checks were absent must not be repeated as current vulnerabilities without revalidation. Remaining assurance gaps include actual provider acceptance, cross-process races on PostgreSQL, unknown external outcomes, source/account binding and capability-specific terminal verification. Persisted audit records and a green invariant scanner are not proof of exhaustive control composition.

## Proposed Universal Tool Gateway / MCP strategy

Extend the existing registry and governed dispatch routes. Add a reviewed server-binding record with fixed transport kind, allowlisted endpoint identity, company account, finite tool-schema digest, health, version and secret reference. Map each remote tool to an existing registered Athena capability with server-owned risk and approval. A remote server's advertised list must never register tools publicly or lower controls.

Treat discovery metadata, descriptions and results as untrusted content. Bound sizes, pagination, timeouts and concurrency; validate responses; strip forbidden data; filter retrieved context by clearance before model use. Require exact action digest and current authorization immediately before dispatch. Reject arbitrary URL/method/body composers, executable paths, server-supplied authority, schema drift and undeclared tools. Use existing persistence, economics, audit, cancellation and reconciliation mechanisms.

Choose one transport and harmless read-only capability first. REST adapters are simpler for small fixed APIs; MCP may reduce integration duplication but adds dynamic discovery/schema/transport attack surface. Neither should become an authority layer above Athena governance.

## Finite declaration coverage

The source catalog contains 72 `defineTool` entries. `02_CAPABILITY_REGISTER.json::finiteToolDeclarations` records each name, declared risk/approval, required capabilities, target, catalog enablement and input/output schema identifiers. `evidence/finite-catalogs.json` additionally indexes integration descriptors, semantic capability catalogs, core-adapter declarations, agent templates and backend/Mac native provider coverage using TypeScript AST literals without executing the source. Helper calls and symbolic references are preserved as declarations. No prompt bodies are exported.

A generated schema identifier such as a tool input/output ID does not prove the corresponding dispatch validator is registered and exercised. Enabled catalog metadata does not guarantee an executable handler, available provider, authorized binding or completed action. Use the significant-capability entry and operation-specific acceptance before making that stronger claim.
